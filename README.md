# mojodojo

**But can it run DOOM?** Playing with the open-sourced [Mojo/MAX](https://github.com/modular/modular) toolchain on an Apple M5 MacBook (32 GB, no Xcode): a toddler-sized int8 accelerator carried from Mojo down to Verilog and into a simulated RISC-V SoC (with Mojo firmware driving it), a DOOM ladder, and some LLM benchmarking.

This is a hobby project and a learning exercise, not a product. Nothing here is fast. Pointers and help are very welcome, see [Help wanted](#help-wanted).

## What's here

| Directory | What it is |
| --- | --- |
| [`fpga/`](fpga/README.md) | A single int8 output-stationary systolic matmul tile (the textbook design from Kung & Leiserson, the kind inside Google's first TPU and Berkeley's Gemmini): a cycle-accurate simulator in Mojo, Verilog generated by Mojo compile-time code, Verilator co-simulation, and Yosys/nextpnr synthesis for a Lattice ECP5 (on paper only, no board yet). |
| [`fpga/phantom/`](fpga/phantom/README.md) | "Phantom NPU": the tile as a simulated device that Mojo and MAX can reach. | [`fpga/tile2/`](fpga/tile2/README.md) | Tile v2: N=8 with on-chip operand buffers, CSRs and a Wishbone slave, generated from Mojo; bit- and cycle-exact Verilator co-sim against a Mojo bus model; ~97 MHz on an LFE5U-85F using 64 of 156 DSPs (synthesis only). |
| [`fpga/soc/`](fpga/soc/README.md) | A LiteX + VexRiscv (rv32im) SoC simulated in Verilator with both tiles on the bus, and DOOM running on the soft core. Upstreams pinned in `fpga/soc/UPSTREAM.md`. |

## Results so far

**The tile** (`fpga/`)
- Generated Verilog matches the Mojo simulator cycle for cycle on 62 co-simulation traces.
- A 16×16 tile places and routes on the largest ECP5 (LFE5U-85F) at about 60 MHz, with multipliers in LUTs.
- All 112 weight matmuls of Llama 3.2 3B routed to the simulated tile give int32 results bit-identical to the same W8A8 maths on the GPU, and identical greedy tokens. Against bf16, 5 of 8 prompts give the same first 8 tokens.
- Projected time to first token for a 512-token prompt: 94.6 s best case (data already on the chip), about 455 s streaming over USB 3, vs 0.63 s on the M5 GPU.

**Tile v2 in a RISC-V SoC, with Mojo on both sides** (`fpga/tile2/`, `fpga/soc/`, `fpga/rvmojo/`, all in simulation)
- Mojo generates the tile's Verilog, and bare-metal Mojo firmware on a simulated VexRiscv core drives it: 5 matmul shapes bit-exact against a Mojo reference on the core, up to 72×600×80 (about 39× faster than the soft CPU alone). C firmware gets the same results.
- The bus is the bottleneck: at 8×256×32 about 97% of the tile path is the CPU storing operands. DMA or double buffering is the next step.
- Synthesis estimates put tile v2 + CPU + SDRAM controller at roughly a quarter of an LFE5U-85F. Not yet on a board.

**Can it run DOOM?** (`doom/`, doomgeneric + Freedoom)
- ✅ Level 1: Mojo drives the game loop.
- ✅ Level 2: DOOM's column/span drawers in Mojo. Frames identical to C, about the same speed.
- ✅ Level 3: the drawing pass as a Mojo Metal kernel on the M5 GPU. 7,116/7,116 frames pixel-identical, about 29× slower than the CPU (per-frame GPU round trip).
- ✅ Level 4 (simulation): unmodified doomgeneric on the VexRiscv soft core in the Verilator SoC, next to the tiles. Title screen and an in-game frame (frame 400) are bit-identical to the host build; about 7 M cycles per frame, so a few fps at 50 MHz. 🔒 On a real board: not yet.

**LLM side**
- At batch-1 decode, memory bandwidth (about 133 GB/s measured, CPU and GPU alike) is the limit, not compute.
- Quality before speed: Llama 3.2 3B wikitext-2 perplexity is +7.25% for MLX 4-bit and +1.72% for llama.cpp Q4_K_M vs 16-bit. For Gemma 3 4B, Google's quantization-aware checkpoint on its native Q4_0 grid is the most faithful 4-bit format (lowest KL divergence).
- Speed-ups (speculative decoding with a small draft model, int8 prefill) are predicted by the roofline model but **not yet timed**.

Timings in this repo are labelled `authoritative` only when taken on an idle machine; everything else is a rough number.

## Where this might go

Musings, not promises:
- Put the simulated SoC on a real ECP5 board (likely a ULX3S 85F) and check it against the simulator; stream the DOOM data from the SD card.
- Feed the tile by DMA instead of CPU stores, so it stops waiting on the bus.
- Build the Mojo compiler from source so the tile gets a real compiler target, not just hand-written drivers.
- Interrupts and a nicer bare-metal Mojo runtime.
- Learn from programmable open accelerators like Georgia Tech's Vortex.

## Reproducing

Each directory's README has exact commands. Common requirements: macOS on Apple Silicon, [pixi](https://pixi.sh) (Mojo/MAX nightly from `conda.modular.com/max-nightly`), [uv](https://docs.astral.sh/uv/), and for `fpga/` the [oss-cad-suite](https://github.com/YosysHQ/oss-cad-suite-build) (Verilator, Yosys, nextpnr). On a Mac with only the Command Line Tools, set `MODULAR_METAL_INTREE_METALLIB=1` (undocumented) so Mojo can build Metal code without Xcode; the pixi environments here set it.

Model weights, the DOOM source and Freedoom data are not in the repo: they are downloaded by the scripts (see `bench/README.md`, `quality/README.md`, `doom/README.md`, `fpga/soc/UPSTREAM.md`) under their own licenses (Llama 3.2 Community License, Gemma Terms of Use, Qwen3 Apache-2.0, doomgeneric GPL-2.0, Freedoom BSD-3-Clause). Absolute paths in logs and result JSON reflect the original machine.

## How it was made

Several AI coding agents worked in parallel, one per directory, with one orchestrator that re-ran every check before a result was committed. The journal in [`docs/grreat/`](docs/grreat/README.md) records what was done, what was verified, and what was decided.
