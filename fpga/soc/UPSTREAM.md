# fpga/soc upstream pins

Everything below is fetched into `third_party/` (gitignored) or the pixi/uv caches; nothing is committed.
`scripts/fetch.sh` reproduces the source checkouts (shallow fetch of the exact commit) and installs
them into the isolated uv venv `fpga/soc/.venv` from local paths (`pyproject.toml` `[tool.uv.sources]`,
`uv.lock`). No global pip, no sudo, `litex_setup.py` not run (only read, to take its pins).

## Toolchain (pixi env `fpga/soc/.pixi`, conda-forge, pinned in `pixi.toml` / `pixi.lock`)

| package | version | license | role |
|---|---|---|---|
| clang | 23.1.4 | Apache-2.0 WITH LLVM-exception | RISC-V cross compiler (`--target=riscv32-unknown-elf`) |
| lld | 23.1.4 | same | linker (`ld.lld`) |
| llvm-tools | 23.1.4 | same | `llvm-ar/objcopy/objdump/nm/readelf/size` |
| meson 1.12.1, ninja 1.13.2 | | Apache-2.0 | picolibc build (driven by LiteX) |
| libevent 2.1.13, json-c 0.19, zlib 1.3.2 | | BSD / MIT / Zlib | linked into LiteX's Verilator sim host modules |

**Compiler choice.** No GCC RISC-V toolchain exists on this Mac (Apple clang has no RISC-V backend; Homebrew has
no LLVM installed). conda-forge `clang` has all LLVM targets, so it is used through GCC-named shims in
`tools/bin/riscv32-unknown-elf-*` (LiteX's VexRiscv CPU has no `clang_triple`, so it only drives the GCC
path). The `-gcc` shim rewrites GCC's `-march=rv32i2p0_m` to `-march=rv32im_zicsr_zifencei`, maps `-N`
to `-Wl,-N`, and links with lld. `LITEX_ENV_CC_TRIPLE=riscv32-unknown-elf` is set by the pixi env.
