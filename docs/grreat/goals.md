# Mojo-native LLM lab on Apple M5

- Outcome: Use the open-sourced Mojo/MAX toolchain on this Apple M5 (32 GB) to understand and push local LLM inference, from silicon (real or invented) to serving, in ways llama.cpp/MLX tutorials don't cover.
- Why: The user values distinctive, toolchain-grounded work over well-trodden paths (GPT-2-in-Mojo, kernel shootouts, MLX LoRA were explicitly passed over).
- Scope and constraints: Apple M5 Mac, macOS 26, no Xcode (Command Line Tools only), Mojo/MAX nightly via pixi. Open-weight 1–4B models. Optional FPGA hardware (Lattice ECP5, open toolchain). Orchestrate via subagents; one writer for these notes.
- Success signals: Both child goals below reach their success signals with evidence recorded in [[analysis]].
- Output — comparison page: a single self-contained HTML page at `~/Desktop/mojo-vs-apple-silicon.html`, regenerated from the project's result JSON, with three parts:
  1. Toolchains side by side, stage by stage: Mojo/MAX (Mojo → KGEN/POP MLIR → LLVM → AIR → in-tree metallib; MAX graph → kernels → serve) vs Apple-native (Metal Shading Language/Swift → `metal` → AIR → metallib; MLX; Core ML → ANE; Accelerate/BNNS → AMX/SME).
  2. Performance across toolchains (MAX vs llama.cpp vs MLX vs Core ML) on the same models and shapes.
  3. Mojo across processors and backends (CPU NEON/SME, GPU simdgroup vs Neural Accelerators, phantom NPU simulator, FPGA when it exists), plus the DOOM ladder results.
- Side quest — "Does it run DOOM?": a tiered test of how far down our stack real DOOM (GPL source via doomgeneric, Freedoom IWAD) can run. Each tier is pass/fail with a captured frame. No re-creation of the game, only the released source and free data.

## Goal 1 — Invented int8 accelerator, from Mojo to (optionally) FPGA

- Outcome: Design a small int8 systolic matmul tile and carry it down the whole stack: Mojo cycle-accurate simulator → Verilog generated by Mojo comptime code → "phantom NPU" compiler + HAL plugin → MAX custom op that offloads Llama prefill matmuls to it → optionally the same RTL on an ECP5 board driven from Mojo.
- Why: Exercises what is unique to the toolchain (comptime codegen, compiler target-plugin ABI, HAL driver ABI, one language from kernel to server). Aimed at prefill because 16-bit decode is memory-bound on every runtime (see [[research]]).
- Success signals:
  - Generated RTL matches the Mojo simulator cycle-for-cycle in Verilator on randomized tests.
  - A Mojo program targets the phantom device (plugin or FFI fallback) and gets bit-exact int8 matmul results.
  - Llama 3.2 3B served by MAX with some prefill matmuls routed to the tile still produces matching greedy output, with simulated cycle counts reported.
  - (Optional) the same RTL runs on an ECP5 and matches the simulator.
- Extension (user direction, 2026-11-08, after the LinkedIn framing): Gemmini-style — a RISC-V soft core beside a bus-attached tile, with Mojo generating the RTL *and* running as bare-metal firmware, and "can it run DOOM?" on that SoC. Added signals:
  - A buffered tile with a bus interface (tile v2) co-simulates bit- and cycle-exact against a Mojo bus model.
  - Bare-metal Mojo firmware on a simulated RISC-V SoC drives the tile bit-exactly.
  - (Hardware) the same SoC on an ECP5 board matches the simulation (folds into G1-E).

## Goal 2 — Processor atlas of the M5, then optimize 1–4B models

- Outcome: Measure every compute engine on this machine — CPU P/E cores (NEON, SME/AMX via Accelerate), GPU (Metal), GPU Neural Accelerators (M5 matmul units), Apple Neural Engine (via Core ML) — for bandwidth and matmul throughput per dtype, then use the atlas to run 1–4B models faster than the best off-the-shelf configuration.
- Why: Knowing where each dtype/shape is fastest tells us how to split prefill vs decode, which quantization to pick, and what Goal 1's tile must beat.
- Success signals:
  - An atlas (data + plots) with measured memory bandwidth and matmul TFLOP/s/TOP/s per engine × dtype × shape, reproducible from scripts.
  - For at least two 1–4B models, a configuration (quantization, engine split, speculative decoding, etc.) that beats the best phase-1 baseline by ≥15% on decode tok/s or TTFT, with quality within 3% perplexity of the bf16 reference (relaxed from 1% on 2026-11-08).

## What would make the goal fail?

- The Mojo/MAX nightly stops running on Apple GPU (e.g. `MODULAR_METAL_INTREE_METALLIB` removed with no Xcode path) and no pinned version can be kept working.
- Results can't be reproduced or compared fairly (concurrent load, prefix caching, mismatched formats) — numbers without a fair method don't count.
- The work collapses into re-implementing what llama.cpp/MLX already do, losing the toolchain-specific angle.
